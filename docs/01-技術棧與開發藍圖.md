# Ai Cad — 技術棧選型與開發藍圖

> 本文件是決策紀錄（ADR 風格），說明「為什麼是這個技術棧」與「系統怎麼切模組」。
> 所有環境數據均為本機實測結果，非推測。

---

## 一、技術棧推薦與理由

### 1.1 硬需求回推

使用者的第一條硬需求決定了一切：

> **Windows 10/11 上雙擊直接執行、完全免安裝任何相依套件的單一 Standalone EXE。**

這條需求會直接淘汰掉一整批看似合理的選項。把它翻譯成工程約束：

| 約束 | 含義 |
| --- | --- |
| 單一檔案 | 不能有 DLL 旁置、不能有 `_internal/` 目錄、不能解壓縮到 temp 才跑 |
| 免安裝相依 | 不能要求使用者裝 Python / Node / .NET Runtime / VC++ Redist |
| 雙擊即執行 | 冷啟動要在 2 秒內看到視窗，否則使用者會以為沒反應 |

### 1.2 候選方案評估（含本機實測）

實測環境（於本機執行指令確認，非假設）：

```
OS        : Windows 11 / amd64
Node      : v22.13.0
npm       : 11.14.0
Go        : 1.23（可用）
Rust      : cargo / rustc → 均不存在
WebView2  : Evergreen Runtime，已安裝（system 層級）
```

| 方案 | 單檔 | 免相依 | 體積 | UI 天花板 | 本機可建置 | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| **Electron** | ✗ | ✗ | 150 MB+ | 高 | ✓ | **淘汰**：必然是一整個資料夾，不可能單檔 |
| **Tauri (Rust)** | ✓ | ✓ | ~8 MB | 高 | **✗** | **淘汰**：需 Rust + MSVC 工具鏈，本機沒有 |
| **PyInstaller** | 偽單檔 | ✓ | 40 MB+ | 低 | 需裝 Python | **淘汰**：onefile 實為自解壓，冷啟動 3–8 秒 |
| **WinUI 3 / WPF** | ✗ | ✗ | — | 中 | — | **淘汰**：需 .NET Runtime 或 self-contained 多檔 |
| **Go + WebView2** | **✓** | **✓** | **~9 MB** | **高** | **✓** | **✅ 採用** |

### 1.3 決策：Go + WebView2 + Vite/React/TypeScript

**放棄 Tauri 的理由**（這是本專案最重要的一次轉向）：Tauri 在紙面上是最漂亮的答案，但它需要 Rust 工具鏈與 MSVC build tools。本機 `cargo` 與 `rustc` 都不存在，要補齊等於要求使用者先裝 ~3 GB 的 Visual Studio Build Tools。這與「免安裝」的專案精神背道而馳，也讓建置環境變得脆弱。**能不能在這台機器上按一個鍵就編譯出成品，是比「哪個框架更潮」更重要的判準。**

**選 Go 的四個理由：**

1. **靜態連結是預設行為。** `go build` 產出的 EXE 不依賴任何外部 runtime。加上 `-ldflags="-H windowsgui"` 就不會彈出黑色主控台視窗。
2. **`go:embed` 把前端整包吃進二進位檔。** 整個 `dist/` 目錄（HTML/CSS/JS）成為 EXE 內的唯讀檔案系統，執行期不落地、不解壓縮、不留暫存檔。
3. **WebView2 已在系統上。** Windows 10/11 現代版本內建 Evergreen Runtime，由 Windows Update 維護。這意味著我們**不用自己扛一顆 Chromium**（Electron 的 150 MB 就是這麼來的），卻能拿到完整的現代 CSS 與 JS 能力——`backdrop-filter`、CSS 巢狀、容器查詢全部可用。這正是「iOS 27 質感」能落地的物質基礎。
4. **記憶體與啟動速度。** 冷啟動 < 1 秒，idle 記憶體約 60–90 MB，是 Electron 的三分之一。

**選 React + TypeScript 的理由：**

這個 App 的核心複雜度不在渲染，而在**狀態**：多個 AI 引擎的設定、逐步生成的進度、歷程樹、多個選區各帶指令。React 的宣告式模型讓「狀態 → UI」這條映射保持可推理；TypeScript 則讓 provider 抽象層的介面契約在編譯期就被檢查——新增一個引擎時，漏實作哪個方法會直接紅字，而不是執行到一半才炸。

**選 Vite 的理由：** 開發期 HMR 毫秒級；production build 產出乾淨的 `dist/`，剛好是 `go:embed` 要的形狀。`vite.config.ts` 刻意設定**相對 base**，因為資產最終由自訂協定（而非 http 根路徑）供應。

### 1.4 完整技術棧

```
┌─ 宿主層 ────────────────────────────────────────────┐
│  Go 1.23 + webview2 binding                        │
│  · go:embed 內嵌前端資產                            │
│  · 自訂 scheme handler 供應資產                     │
│  · -H windowsgui（無主控台）                        │
│  · goversioninfo（圖示、版本資訊、Manifest）        │
└────────────────────────────────────────────────────┘
┌─ 前端層 ────────────────────────────────────────────┐
│  Vite 6 + React 19 + TypeScript 5                  │
│  · 零 UI 套件依賴（primitives 全自製）              │
│  · 零圖示套件依賴（icons 全自繪）                   │
│  · CSS custom properties 作為 design token          │
└────────────────────────────────────────────────────┘
```

**刻意不引入的東西**，以及原因：

- **UI 元件庫**（MUI / Ant / shadcn）：它們的預設視覺語言就是「AI 工具味」的來源。要做出原創質感，元件必須自己長出來。
- **圖示庫**（Lucide / Heroicons）：混搭圖示庫會讓線寬、端點、視覺重心不一致，這是廉價感最主要的來源之一。全部自繪，統一 20×20 網格、1.5px 線寬、圓角端點。
- **狀態管理庫**（Redux / Zustand）：Phase 1 的狀態規模用 `useState` + `useMemo` 就夠，過早引入會增加閱讀成本。
- **CSS 框架**（Tailwind）：本專案的視覺一致性靠 design token 強制，而非 utility class。

## 二、開發藍圖與模組劃分

### 2.1 分層原則

**單向依賴，UI 永遠在最外層。** 任何一層都不得反向 import 上層。這條紀律讓「換一個 AI 引擎」不會動到 UI，「換一套 UI」不會動到 provider。

```
┌───────────────────────────────────────────────────────┐
│  ui/               React 元件（唯一知道 React 的層）   │
│  ├─ App.tsx        三欄 shell 組裝 + 全域狀態          │
│  ├─ IntentPanel    圖面規格輸入                        │
│  ├─ DrawingCanvas  圖面顯示 + 選區框選                 │
│  ├─ SettingsSheet  引擎設定浮層                        │
│  ├─ primitives/    Button / Field / Toggle / Segmented │
│  └─ icons.tsx      自繪圖示集                          │
└──────────────────────┬────────────────────────────────┘
                       │ 只呼叫 generate() / inpaint()
┌──────────────────────▼────────────────────────────────┐
│  core/pipeline/orchestrator.ts                        │
│  編排層：意圖 → 精煉 → 提示語 → 引擎 → 圖面           │
│  UI 不知道 provider 的存在，只知道這兩個函式           │
└───┬────────────┬─────────────┬───────────────────────┘
    │            │             │
┌───▼──────┐ ┌───▼─────────┐ ┌─▼──────────────────────┐
│ prompt/  │ │ providers/  │ │ settings.ts secrets.ts │
│ builder  │ │ registry +  │ │ 設定持久化 / 憑證保管   │
│ 純函式   │ │ 各 adapter  │ │                        │
└──────────┘ └───┬─────────┘ └────────────────────────┘
                 │
         ┌───────▼──────────────────────────────┐
         │  core/net/transport.ts               │
         │  唯一對外出口 (single egress)         │
         └──────────────────────────────────────┘
                 │
         ┌───────▼──────────────────────────────┐
         │  core/types.ts  領域型別（零依賴）    │
         └──────────────────────────────────────┘
```

### 2.2 各模組的職責與設計要點

#### `core/types.ts` — 領域型別
不依賴 React、不依賴任何 SDK，只描述「圖面」這件事：`DrawingKind`（八種圖面類型）、`AnnotationSpec`（標註慣例）、`DrawingIntent`（使用者意圖的完整表達）、`MaskRegion`（選區，**用 0..1 正規化座標**，與圖片解析度解耦）、`Artboard`（一次產出，含 `parentId` 形成歷程樹）。

**設計要點：** `Artboard` 保存 `resolvedPrompt`。專業工具必須可重現、可除錯——使用者要能看到「到底送了什麼給模型」。

#### `core/providers/*` — 引擎抽象層（Ports & Adapters）

關鍵設計決策：**把「文字能力」與「影像能力」拆成兩組獨立的能力宣告。**

```ts
interface ProviderCapabilities {
  text: boolean;           // 能精煉提示語
  imageGenerate: boolean;  // 能出圖
  imageInpaint: boolean;   // 能遮罩局部重繪
  vision: boolean;         // 能讀圖
}
```

為什麼重要：OpenAI / Claude / Gemini / Grok 都能做提示語精煉，但只有部分能出圖；本地 SD 只能出圖不能精煉；Ollama 只能精煉。若不拆開，UI 就得寫滿 `if (provider === 'xxx')` 的特例——那是技術債的溫床。拆開後，**UI 只查詢能力，不認識具體引擎**。

已實作的 adapter：

| 檔案 | 覆蓋的引擎 |
| --- | --- |
| `openaiCompatible.ts` | OpenAI、xAI Grok、**第三方聚合／中轉自定義 API**、Ollama（`/v1` 相容端點） |
| `anthropic.ts` | Claude（`x-api-key` + `anthropic-version` 標頭，格式與 OpenAI 不同） |
| `gemini.ts` | Gemini（含影像生成與局部重繪） |
| `sdWebui.ts` | 本地 Stable Diffusion（AUTOMATIC1111 / Forge / reForge） |

`openaiCompatible.ts` 用**工廠函式**產生四個 adapter，差別只在 `baseUrl`、預設模型與能力宣告。避免四份幾乎一樣的檔案。

**新增引擎的成本：** 寫一個 adapter 檔 + 在 `registry.ts` 加一行。UI 零改動。

#### `core/prompt/builder.ts` — 提示語建構層

**這一層是「專業級圖面」與「工程圖的插畫」之間的分界線。**

直接把使用者的一句話丟給繪圖模型，得到的必然是「看起來像工程圖但完全不能用」的東西。要得到可讀的圖面，必須把意圖編譯成有固定骨架的指令：

```
視角規則 → 線條規則 → 標註規則 → 尺寸清單 → 排除清單
```

實作要點：
- `KIND_SKELETON`：八種圖面類型各有預寫的視角與構圖骨架（例如機械零件 = 三視圖 + 等角詳圖；P&ID = ISA 儀表泡 + 流向箭頭）。
- `LINE_STYLE_CLAUSE`：四種線條風格對應具體的媒材與筆觸描述，**含明確的線寬階層**（0.7mm 輪廓 / 0.35mm 隱藏線 / 0.25mm 尺寸線）——這是讓圖看起來「專業」的關鍵細節。
- `measurementBlock`：使用者填的尺寸會被寫成 `MUST appear verbatim`，強制數值逐字出現。
- `BASELINE_EXCLUDE`：無論使用者怎麼設定，永遠排除寫實渲染、戲劇打光、投射陰影、色彩漸層、裝飾背景、浮水印、鏡頭模糊。
- `REFINE_SYSTEM_PROMPT`：文字模型的精煉指令**明令禁止它發明尺寸數值**，也禁止它談論風格、光影、鏡頭——只准描述幾何。

**整層皆為純函式**，可單元測試、可重現。

#### `core/pipeline/orchestrator.ts` — 編排層

把「意圖 → 提示語 → 引擎 → 圖面」這條流水線收在一處，對 UI 只暴露 `generate()` 與 `inpaint()`。

兩個值得說明的實作決策：

1. **精煉失敗不讓整次生成失敗。** 提示語精煉是加分項，若文字引擎超時或報錯，直接退回未精煉的草稿繼續出圖。使用者要的是圖，不是錯誤訊息。
2. **精煉結果只替換主體那一行。** 用 `draft.replace(/^Subject: .*$/m, ...)` 精準置換，骨架與標註規則保持不動。若讓文字模型改寫整份提示語，可控性會瞬間崩潰。
3. **遮罩合成在前端 canvas 完成。** 多個選區合成成一張黑底白框 PNG（A1111 與 Gemini 都吃這個慣例），並把各選區的指令編號後合併成一次請求。

#### `core/net/transport.ts` — 唯一對外出口

**所有外呼集中在這一個檔案。** 這不是為了節省程式碼，而是為了讓下列事情各只有一個實作點：逾時控制、AbortSignal 串接、錯誤正規化（HTTP 狀態 → 可讀中文訊息 + 修正建議）、未來的代理設定、以及**安全審查**。要確認這個 App 有沒有把資料送到不該去的地方，只需要讀這一個檔。

#### `core/secrets.ts` — 憑證保管橋接層

API 金鑰**不與一般設定混存**。這一層是一個介面，目前有記憶體實作（開發模式，關閉即清除），並預留 `kind: 'os-keychain'` 分支——Phase 3 由 Go 宿主接上 Windows DPAPI，透過 bridge 呼叫。

配套設計：`ProviderConfig` 裡存的是 `secretRef`（鍵名）而非明文；`maskSecret()` 只回傳遮罩形式，**UI 永遠無法還原明文**；匯出設定檔時憑證不會被帶出去。

#### `core/settings.ts` — 設定持久化
含版本號與遷移邏輯，避免日後改欄位時把舊使用者的設定弄壞。設定變更**立即持久化**，不設「儲存」按鈕——專業工具不該讓使用者承擔忘記存檔的風險。

### 2.3 開發階段規劃

| Phase | 範圍 | 狀態 |
| --- | --- | --- |
| **0** | 環境驗證、技術棧決策 | ✅ 完成 |
| **1** | Core 層 + 三欄 shell + 設定浮層 + 選區框選；`tsc` 與 `vite build` 通過 | ✅ 完成 |
| **2** | Go 宿主：`go:embed` + WebView2 視窗 + 單一 EXE 建置與雙擊驗證 | ▶ 下一步 |
| **3** | 宿主橋接：DPAPI 憑證、原生檔案對話框、匯出 PNG/SVG/PDF | 待辦 |
| **4** | 向量標註疊層：在 AI 底圖上疊可編輯的 SVG 尺寸線（真正精確的數據標註） | 待辦 |
| **5** | 打磨：圖示與版本資訊、自動更新檢查、鍵盤快捷鍵完整化 | 待辦 |

### 2.4 Phase 4 的必要性（架構前瞻）

必須誠實記錄一個工程現實：**擴散模型畫不出可信的尺寸數字。** 它能畫出「看起來像尺寸標註」的線與符號，但數值經常是錯的或歪的。

因此 Phase 4 的向量疊層不是加分項，而是**讓「精確的數據／尺寸標註」這條需求真正成立的關鍵**：AI 負責幾何與視角（它擅長的），SVG 疊層負責尺寸線、箭頭與數值（它不擅長的）。使用者填在左欄的尺寸會成為可拖曳、可編輯、匯出後仍精確的向量物件。

目前的架構已為此預留位置：`Artboard.intent.measurements` 保存了結構化的尺寸資料，`DrawingCanvas` 的正規化座標系統可直接承載疊層，兩者都不需要重構。
