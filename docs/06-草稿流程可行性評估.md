# 草稿 → SVG → 生圖：可行性評估與實作說明

本文件回答一個問題：**「先讓文字模型用 SVG 畫出 CAD 草稿，再交給生圖模型出圖」這條路可行嗎？**
結論是可行，但原始構想有幾個會直接失敗的地方；以下說明哪些成立、哪些必須改、以及最後實際
落地的設計。

---

## 1. 為什麼要換生成方式

原本的流程是「一句需求 → 生圖模型直接出整張圖」。擴散式生圖的強項是質感，弱項是約束求解：
它一次要同時滿足視角、線寬、投影符號、標註、留白、文字語言，結果常見比例走鐘、前視圖與
側視圖對不齊、尺寸標註亂畫。

把工作拆成兩段，各交給擅長的一方：

| 階段 | 執行者 | 產出 | 為什麼適合 |
| --- | --- | --- | --- |
| 擬稿 | 文字模型 | 可解析的 SVG 線稿 | 擅長幾何推理與座標計算 |
| 出圖 | 生圖模型 | 完稿圖 | 擅長線條質感與整體版面 |

關鍵是**文字模型會真的算出座標**，而不是再寫一段形容詞。這正是原本流程缺少的「版面依據」。

## 2. 原始構想的四個問題（實測發現）

### 2.1 SVG 常常是壞的 —— 必須假設它壞

文字模型產出的 SVG 五花八門：夾在 ``` 圍籬裡、前面多一段說明、缺 viewBox、用了會爆版的巢狀
`transform`、塞了一堆 `<text>`、顏色亂填、輸出被長度上限截斷而沒有 `</svg>`。

因此**不信任模型輸出**，一律經過 `normalizeDraftSvg`：

- 外層 `<svg>` 由程式自己重寫，`width`／`height`／`viewBox` 寫死為 1000×700。
  少了內在尺寸，各家引擎對點陣化的解讀不一致，藍圖可能只渲染出一小角。
- 只放行幾何元素（line／polyline／polygon／rect／circle／ellipse／path／g）。
- 顏色一律壓成黑線、`fill="none"`。少了 `fill="none"` 的圖形會被黑色填滿，整張草稿就毀了。
- 移除外部參照（`href`、`url(...)`、`javascript:`、`data:`）—— 草稿來自第三方模型，
  不能讓它把遠端資源或可執行內容帶進渲染流程。
- 保留 `stroke-width` 與 `stroke-dasharray`：線寬與虛線是工程圖語意，不是裝飾。
- 截斷的草稿仍然救得回來：`extractSvg` 容許沒有收尾標籤，`normalizeDraftSvg` 自行補齊元素結構。

### 2.2 各家引擎對「附圖」的語意不同

Gemini 把附圖當編輯底稿；OpenAI 相容介面一旦帶圖就會改走 `/images/edits`。硬附圖會讓
沒有實作該端點的引擎直接失效，連本來能用的設定一起壞掉。

處理方式：**由引擎能力決定要不要附圖**。只有具備局部重繪（可處理輸入影像）能力的引擎才收到
草稿 PNG；其餘引擎收到的是同一份草稿的**文字幾何摘要**。兩種版本都先備好，等抽到實際引擎
才決定用哪一份。

### 2.3 純文字模型不是保證

使用者可能沒接文字模型，或文字模型回了「我沒辦法畫」這類非 SVG 內容。此時整條草稿階段視為
沒有草稿，**退回原本的單段流程**——生成不能因為草稿壞掉而整個失敗。草稿階段本身也包裹在
try/catch 中，例外只會讓它安靜消失。

### 2.4 多跑一次文字模型 = 多一次延遲與費用

草稿成功時，原本的「精煉主體描述」步驟就沒有意義了：草稿已經把實際幾何與視圖擺位寫成座標，
資訊量高於一段文字描述。所以只有在**草稿失敗**時才走原本的精煉路徑，既有行為不變，成功路徑
反而少一次往返。

## 3. 實際落地的設計

```
使用者需求
   │
   ├─ [草稿階段] 文字模型（獨立 system instruction，要求輸出純 SVG）
   │      └─ extractSvg → normalizeDraftSvg → summarizeDraft
   │             ├─ 藍圖點陣化為 PNG（渲染失敗則只留摘要）
   │             └─ 失敗 → 視為沒有草稿，走原本流程
   │
   └─ [出圖階段] buildPositivePrompt（原有骨架不放棄，草稿只做「追加」）
          ├─ 引擎有能力收輸入影像 → prompt + 草稿 PNG（排在使用者參考圖之前）
          └─ 否則                 → prompt + 文字幾何摘要
```

幾個刻意的取捨：

- **提示詞用「追加」而非「改寫」。** `buildPositivePrompt` 產生的視角／線條／排除規則是
  經過測試的骨架，草稿只補上它不知道的部分：這張圖實際長什麼樣。任一段出錯都不會互相拖累。
- **草稿排在參考圖之前。** 模型會把「第一張圖」當版面依據；使用者的參考圖是外觀參考，
  不該被當成新版面。
- **藍圖依線條風格反相。** 藍圖風格＝深底白線，先反相再畫線，讓參考底稿跟成品同一種視覺語言。
- **摘要上限 1400 字元。** 提示詞不是日誌，過長反而稀釋重點。
- **新增獨立的進度階段 `drafting`。** 介面能顯示「正在擬稿」，不會讓使用者以為卡住。

## 4. 可擴充性：草稿階段能送自己的 system instruction

原本 `REFINE_SYSTEM_PROMPT` 是硬寫在三個 provider adapter 裡的常數，草稿階段沒辦法要求
「輸出 SVG」這種不同的任務。現在改由 `systemInstructionFor(input)` 決定：

- 未覆寫 → 沿用原本的精煉指令，既有行為完全不變。
- 有覆寫 → 用新指令，並可附加當輪指示。
- 空白覆寫視為未提供，不會送出空的系統指令。

  `npm run build` 通過、Windows 打包與 EXE 圖示／版本資源檢查通過。

## 6. 已知限制

- 草稿品質取決於文字模型的幾何能力。弱模型會畫出比例不對的草稿，此時**帶摘要的文字版**
  通常比硬附一張爛圖好——這是刻意的降級路徑，不是缺陷。
- 標註數值不由草稿產生。草稿階段被明確要求不要編造尺寸數字；精確文字與數值仍由應用程式
  以向量方式繪製，維持既有「文字不依賴生圖模型」的設計。
- 尚未對真實 Gemini／OpenAI 端點做帶憑證的 E2E 驗證；目前涵蓋到接線與降級行為。
